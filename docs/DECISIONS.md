# Decisions & Assumptions Log

Per PRD §15: every assumption made during implementation is recorded here.

## Stack

- **Auth: Clerk** (not Supabase Auth as suggested in PRD §7). PRD marks the recommended stack as "[ASSUMPTION — any equivalent is acceptable]". This environment is Vercel-native; Clerk is Vercel's preferred native Marketplace auth integration (auto-provisioned env vars, unified billing). Covers FR-1/FR-2/FR-3.
- **Database: Neon Postgres** (not Supabase Postgres). Same rationale — Neon is Vercel's preferred native Marketplace Postgres. Using Drizzle ORM (`drizzle-orm/neon-http`) per `vercel-storage` skill guidance.
- **Storage: Vercel Blob** (not Supabase Storage / Cloudflare R2). Native Vercel product, supports both public and private access, client-side multipart/resumable upload up to 5TB — fits FR-4's resumable upload requirement directly.
- **Realtime/progress (FR-37): polling**, not a realtime subscription. Neon has no built-in realtime channel like Supabase; FR-37 explicitly allows "polling or server-sent events / realtime subscription," so the worker writes job progress to the `Job` row and the client polls `GET /api/projects/:id`.
- **Row-level access control (NFR Security):** enforced at the application/API layer (every query scoped by the authenticated Clerk `userId`), not via Postgres RLS. Neon does not have Supabase's built-in `auth.uid()`-integrated RLS; Clerk is not a Postgres-native identity provider. This is an architecture deviation from the PRD's literal "Row-level access control" phrasing but satisfies the same goal (FR-2: users only see their own data). Revisit if compliance requirements later demand DB-enforced RLS.
- **M3.1 STT provider: OpenAI's hosted Whisper API** (`whisper-1`, `/v1/audio/transcriptions` with `timestamp_granularities=["word"]`), not self-hosted faster-whisper/WhisperX. Consistent with the already-recorded "hosted APIs for v1" assumption (open question #4 below). Called directly from the Python worker (`worker/transcribe.py`) via `STT_API_KEY` — no Vercel product involved.
- **M3.3 Speaker diarization: deferred, not implemented.** The chosen STT provider (OpenAI Whisper API) doesn't offer diarization. FR-10 says "where available" — for v1, nowhere is available, so `speaker` stays unset on every transcript word/segment. Revisit if a diarization-capable provider (e.g., a dedicated diarization API, or self-hosted WhisperX with pyannote) is added later; this also means M4.2's reframing can't yet use per-speaker turn-taking to decide who's "active," only face detection.
- **M3.2 "flag low-confidence segments" (mixed-language edge case): approximated via Whisper's `avg_logprob`,** not a real per-segment language-confidence signal (Whisper doesn't expose one). A segment is flagged `lowConfidence` when `avg_logprob < -1.0`. This is a proxy, not a precise language-switch detector — revisit if mixed-language accuracy becomes a real complaint.
- **M3.8 "no speech detected": implemented as report-and-stop only.** The edge case's other branch — "offer audio-energy-based highlights" — is NOT implemented. Detection uses Whisper's `no_speech_prob` (worker/transcribe.py); if every segment looks like silence/music, the ingest... transcribe stage fails clearly with "No speech detected in this video" rather than silently producing an empty transcript. Revisit if this proves too aggressive (e.g., rejects long musical intros in otherwise-fine videos).
- **M3.5 LLM moment-detection runs in the Next.js app, not the Python worker** (`src/app/api/internal/detect-moments/route.ts`), using the AI SDK (`generateObject` + Zod) through Vercel AI Gateway — Gateway and the `ai` package are TS-native; there's no equivalent for direct use from Python, and Gateway gives the cost/observability NFR (§6, FR-44) essentially for free. The worker's `detect` stage just POSTs `{projectId}` to this route (authenticated via a shared `WORKER_INTERNAL_SECRET` header, since it's machine-to-machine, not a Clerk user session) and waits for the synchronous response; the route itself reads the transcript, calls the LLM per chunk, validates/snaps/dedups/filters, and writes Clip rows directly. Model: `anthropic/claude-sonnet-4.6` via the gateway string — swap freely, no code changes needed elsewhere.
- **Worker-local source storage (M2.3 ingest stage):** the raw source video (YouTube download, or the local copy of an uploaded file) lives on the worker's own disk under `WORKER_STORAGE_DIR` (default `/data/nabd/<projectId>/`), not in Vercel Blob. Rationale: there is no official Vercel Blob client for Python, and the JS SDK's HTTP contract is internal/versioned (`x-api-version`, currently 12) — reimplementing it in Python would be brittle. The product never needs to let a user download the *original* source (only rendered clips, M4/M5, which the worker already needs to push somewhere downloadable), so the source only ever needs to be resolvable by the worker itself across pipeline stages. For `sourceType: "upload"`, `project.storageKey` stays the public Blob URL set by `/api/upload` (the worker just downloads it locally for ffprobe/ffmpeg); for `sourceType: "youtube"`, `project.storageKey` is set to the worker-local path after a successful ingest. **This assumes the worker runs as a single instance (or replicas sharing one mounted volume)** — an autoscaled fleet of stateless containers would lose the file between stage transitions. Matches the open "worker hosting budget" question (#3 below); revisit if hosting choice can't provide a persistent volume.
- **M4.2 face detection: MediaPipe's legacy `solutions.face_detection` API, pinned to `mediapipe==0.10.21`.** MediaPipe's current release (1.x) dropped `solutions` in favor of a Tasks API that needs a `.task` model file downloaded at runtime — a network dependency and moving part the Docker image shouldn't need. `0.10.21` bundles its model in the pip package (fully offline-capable, verified locally) and matches the PRD's literal suggestion (§7: "MediaPipe... for face detection"). Revisit if the legacy API is ever fully removed from PyPI.
- **M4.2 reframing fallback split:** "no face detected in ≥70% of sampled frames" → blurred-background letterbox; "≥2 faces in ≥30% of sampled frames" (ambiguous active speaker) → static center crop; otherwise → face-tracked crop with an EMA-smoothed horizontal pan. This maps PRD §11's one sentence ("Fallback: center crop, or blurred-background letterbox if no face is found") onto two distinct trigger conditions since the PRD names two fallbacks but only one trigger. Thresholds (70%/30%) are a first guess, not tuned against real footage — revisit once real videos are available to eyeball.
- **M4.3/M4.5 render pipeline verified locally against a full-featured ffmpeg build (Windows, gyan.dev "full" build — libx264/libass/libfribidi/libharfbuzz/loudnorm all present), not yet against the worker's actual Debian/apt ffmpeg package in Docker.** All four reframe strategies, the karaoke `\k` subtitle sweep (confirmed via pixel sampling — highlighted-word pixel count increases monotonically as playback advances through a caption card), and Arabic RTL shaping (confirmed via non-blank pixel output, libass+fribidi+harfbuzz) were exercised end-to-end with synthetic ffmpeg-generated sources — real verification, not blind wiring. Debian's `ffmpeg` apt package also ships with libass enabled in practice, but this hasn't been re-verified inside the actual container — confirm on first deploy.
- **ffmpeg `-ss`/`-to` as input options reset the filter-graph's `t` clock to ~0 at the seek point** (empirically verified: a crop-position expression keyed to absolute source time only took effect when re-based to be relative to the cut's own start). Because of this, `render.py` converts every transcript word/segment and face-detection sample to clip-relative time (`t - clip.start_s`) before building ASS subtitles or the face-track crop expression — anything using ffmpeg's `t` in a filter must do the same.
- **M4.9 signed download links: custom HMAC tokens (`src/lib/download-tokens.ts`), not Vercel Blob's `issueSignedToken`/`presignUrl`.** Blob's presign API is a delegation system (hand a *third party* standing authority to mint its own URLs via an HMAC it holds) — a different problem from "give the current authenticated user a link that still works in 24h." Rolling a minimal HMAC-over-`{clipVersionId, kind, exp}` token is simpler, fully testable without live Blob credentials, and satisfies FR-34 directly: `GET /api/clips/:id/download` (Clerk-protected) mints the token, `GET /api/download/:token` (unprotected — the token *is* the auth) verifies it and streams the private blob via `get(key, {access:"private"})`. Revisit only if a real need for delegated/third-party signing shows up.
- **M4.9 storage split: video/SRT/VTT private, thumbnail public.** Thumbnails are gallery previews, not an audited download — serving them as plain public Blob URLs avoids minting a signed link on every gallery page load. Everything a user actually "downloads" (FR-33) stays private behind the signed-token flow above.
- **Clip output paths are per-*version*, not per-clip** (`clips/<clipId>/<randomVersionKey>/...`), so a re-render (M5) never overwrites a still-downloadable prior version's files — required for FR-32 ("previous version stays downloadable until replaced").
- **M4 render-stage failure handling: per-clip, not all-or-nothing.** `run_render` renders every pending clip for a project independently; one clip's ffmpeg failure marks only that clip `failed` and moves on. The job stage itself only fails (blocking the pipeline / surfacing to the user) if *every* clip failed. Rationale: partial success (7 good clips, 1 bad) is a much better user outcome than losing all 8 because of one edge case.
- **M5.4 re-render reuses the project-level `render` job stage as-is, with no new job/clip-linkage column.** `POST /api/clips/:id/render` just flips that one clip's `status` back to `pending` and queues a `stage: "render"` job; the worker's existing `run_render` (which already renders "every pending clip for the project") naturally renders only that one clip, since it's the only one pending. This only stays correct because the worker is a single instance processing jobs strictly in order (already an established assumption — see "worker-local source storage" above); revisit together if that assumption ever changes.
- **M5.2/M5.3 trim + subtitle-text-edit correctness is client-enforced, not re-validated server-side beyond the ±30s bound.** `PATCH /api/clips/:id` validates the *trim* bound (`src/lib/trim.ts`, tested), but "timing kept" for subtitle text edits (FR-31) — i.e., a `subtitleWords` PATCH must reuse each word's original start/end and only change its text — is trusted from the client, not re-derived/verified server-side. A malicious or buggy client could desync captions from audio. Revisit if that turns out to matter (e.g., re-validate that submitted word timestamps are a subset of the transcript's own word timestamps).
- **M5.7 ZIP export runs synchronously in a Vercel Function** (`/api/clips/export`), not as a worker job, despite PRD §9 calling it "async." Rationale: FR-36's "never process video in a request handler" is about encoding/transcoding; bundling already-rendered MP4s into a ZIP is pure I/O, comfortably inside a Function's 300s/100MB limits for a selection of short social clips. Revisit (move to a worker-driven job + polling) if exports of many/long clips become common enough to risk the timeout/size ceiling.
- **M5.7 export ZIPs are private Blob objects at `exports/<uuid>/clips.zip`**, downloaded through the same signed-HMAC-token flow as clip versions (`download-tokens.ts`'s payload is now a `{type: "clip-version"} | {type: "export"}` union) rather than Blob's presign/delegation API — same rationale as M4.9 above. Nothing currently deletes old export ZIPs; they'll accumulate in the store. Revisit alongside the general data-retention pass (M8.4).
- **M6.1 translation never trusts the LLM with timing at all.** `/api/internal/translate-subtitles` sends only each segment's *text* to the model and asks for translated strings back in the same order/count; the resulting `TranscriptSegment[]` is built by zipping those strings onto the *original* segments' start/end locally. This makes FR-25 ("timing kept aligned per segment") true by construction rather than by validating the model's echoed numbers — a stricter, simpler guarantee than the moment-detection route gets for its own timestamps. `src/lib/dubbing.ts`'s `validateTranslatedAlignment` still runs as a defense-in-depth check (catches a wrong segment count or empty translation).
- **M6.1 translated captions are segment-level static text, not word-by-word karaoke.** There's no reliable way to get per-word timing for translated text (word count/order differs from the original), so `subtitle_lang_preference: "translated"` renders via `subtitles.build_ass_plain` (one static Dialogue event per segment, char-wrapped to ≤2 lines) instead of the karaoke `build_ass` path used for original-language captions. This is a deliberate reading of FR-25's literal "timing kept aligned **per segment**" (not "per word").
- **M6.2 TTS provider: OpenAI's hosted TTS API** (`tts-1`, `/v1/audio/speech`), called directly from `worker/dub.py` via `TTS_API_KEY` — consistent with the "hosted APIs for v1" assumption and PRD §7's own example ("TTS API (e.g., ElevenLabs / OpenAI TTS)"). A single stock voice (`alloy`) is used for every dub; no cloning provider is wired up (next point).
- **M6.3 voice cloning: gate implemented and tested (`can_use_voice_cloning` in both `src/lib/dubbing.ts` and `worker/dub.py`), but no actual voice-cloning TTS provider is integrated.** Every dub uses the stock OpenAI voice regardless of the `voiceCloningEnabled`/`voiceCloningConsent` project options — those flags are captured in the New Project UI and persisted, and the gate function that would guard a real cloning call is unit-tested (FR-26's "opt-in with explicit consent" requirement), but wiring an actual cloning-capable provider (with voice-sample upload, consent audit trail, etc.) is a separate, larger integration deferred to when it's actually prioritized.
- **M6.3 source separation ("mix under original background audio if available") is NOT implemented — dubbing always replaces the voice track,** the PRD's other branch ("otherwise replace the voice track"). Real vocal/background source separation (e.g., Demucs/Spleeter) is a heavy ML dependency (large model download, GPU-preferred) out of proportion for this slice, and the PRD itself frames it as conditional ("if available"). Revisit if losing original background music/ambience during dubbed playback becomes a real complaint.
- **M6.2/M6.3 dub audio time-fitting: `librubberband`'s `rubberband` ffmpeg filter (`tempo=` param), not the more common `atempo`.** The worker's ffmpeg build already includes it (`--enable-librubberband`), and it time-stretches without the pitch/robotic artifacts `atempo` introduces past small ratios — verified empirically (a 3s tone at `tempo=1.5` produces a 2.0s output, i.e. `tempo` divides duration, matching `plan_dub_timing`'s ratio convention) and further exercised in `test_render_integration.py::TestDubAudioAssembly`.
- **M6.4 dubbed audio and translated subtitles are prepared eagerly (by the `dub`/`translate` stages) but only burned into a new ClipVersion when the user explicitly picks them in the clip editor and re-renders.** The automatic M2-M4 pipeline always auto-renders with original audio/captions; `clips.audio_preference`/`subtitle_lang_preference` (defaulting to "original") are what the *next* re-render reads — matching FR-27's framing as a clip-editor action, not something that happens to every clip automatically. If a clip's dub track isn't ready yet when a "dubbed" re-render runs (e.g., the `dub` stage hasn't finished), `run_render` silently falls back to the original audio rather than failing the render — revisit if that's too silent (e.g., surface a warning to the user instead).
- **M7.3 Stripe is NOT installed — blocked on the same Vercel Marketplace terms-acceptance bug already logged for Clerk/Neon.** Per the `marketplace` skill's rule ("never hand-wire a provider SDK from memory, substitute a mock, or scaffold a stand-in to wire later"), no Stripe-specific code (checkout sessions, webhooks, subscription sync) has been written — that would be throwaway work. Everything else in M7 that doesn't depend on payments (plan tiers, metering, cap enforcement, watermark, account UI) is implemented and real. The Account page's "Upgrade" button is present but disabled with an honest explanation, not a fake checkout link. Retry `vercel integration add stripe` once the Marketplace bug is resolved, then build FR-43 for real against the provisioned env vars.
- **M7.1 paid-tier minutes (300/month) and per-unit cost estimates (STT/TTS/compute $ rates) are placeholder figures [ASSUMPTION], not sourced from a live pricing API or a real per-provider invoice.** PRD leaves the paid allowance unspecified ("more minutes") and only asks that cost be logged, not that the figure be exact. `src/lib/pricing.ts`'s LLM rate and `worker/usage.py`'s STT/TTS/compute rates are all in the same boat. Revisit once real Stripe plans (M7.3) and real usage data exist to calibrate against.
- **M7.2 metering happens at the `ingest` stage (once source duration is known), not at `render`/project-completion.** This means a project that fails partway through (e.g., at `detect` or `render`) still counts its source-minutes against the user's allowance — the PRD doesn't specify whether a failed job should refund its minutes, and charging for the STT work that *did* happen (which is real, sunk cost) seemed the more defensible default. FR-44's "refund minutes" (admin, M8.1) is the intended escape hatch for support to reverse this when warranted.
- **M7.2 "period" is a rolling 30-calendar-day window from `users.period_reset_at`, checked and rolled over lazily on the next `/start` call** — not a real monthly billing-cycle boundary from a Stripe subscription (there is no subscription yet, M7.3). Revisit once Stripe billing periods exist; they should become the source of truth instead.
- **M7.4 the dubbing-requires-paid-plan gate and the out-of-minutes gate both live in `POST /api/projects/:id/start`, checked only when `project.status === "created"`** (a fresh start, not a retry) — matching edge case §11's "let in-flight job finish": since minutes are only gated at the *start* of a fresh project, nothing in this codebase ever cancels a job that's already running, so that half of the edge case is satisfied by simply not building a cancellation path, not by explicit logic.
- **M7.5 "720p"/"1080p" are the short (width) edge of the 9:16 portrait output**, not a literal video "height" despite `PLAN_LIMITS.maxHeight`'s name (kept for continuity with the PRD's own "max 720p"/"1080p" wording) — 1080x1920 is what's conventionally called "1080p" vertical video. `worker/main.py`'s `run_render` converts width->height via the fixed 9:16 aspect ratio before calling `render_clip`.
- **M7.5 watermark is `drawtext`, not a logo image** — simpler (no image asset/PNG-overlay filter needed) and the PRD doesn't specify a design, just "watermark on exports." Requires a font file in the worker image (`fonts-dejavu-core`, added to the Dockerfile); verified for real locally against a matching local font (Windows' Arial Bold) via pixel-sampling the bottom-right corner of a fully black synthetic render.
- **M8.1 admin access uses Next.js's built-in `forbidden()`** (`next.config.ts`'s `experimental.authInterrupts: true`), not a custom error/redirect — it's the documented, version-matched way to do a role check in this specific Next.js release (confirmed against `node_modules/next/dist/docs`, since this app's Next.js has been explicitly flagged as non-standard/breaking relative to training data). No self-serve admin invite flow exists; promote a user with `UPDATE users SET is_admin = true WHERE id = '...'` directly in the DB.
- **M8.2 Sentry is NOT installed — same Vercel Marketplace terms-acceptance bug as Clerk/Neon/Stripe**, this time in the `observability` category. Per the `marketplace` skill's rule, no `@sentry/nextjs` (or worker equivalent) code was hand-wired. Built structured JSON logging instead (`src/lib/log.ts`, `worker/log.py`) as real, working groundwork — swapping in actual Sentry calls later is a mechanical find-and-replace of the `log.error(...)` call sites, not a redesign. Per-job cost, the other half of M8.2, is already real and surfaced in the admin dashboard (M8.1).
- **M8.3 edge-case sweep found and fixed three real gaps**, rather than everything already being covered by earlier milestones: (1) the "reject an over-long upload before it finishes" check existed server-side (`validateDuration`) but was never called from the New Project form — added a client-side `<video>`-metadata read (fast, no full download) before upload starts; (2) the client upload call never actually requested multipart chunking (`multipart: true` was never passed to `@vercel/blob/client`'s `upload()`) — fixed, restoring the auto-retry-failed-parts behavior FR-4 asks for; (3) "admin can disable accounts" had no implementation at all — added `users.is_disabled`, an admin toggle, and enforcement at both project creation and start.
- **M8.3 resumable upload across a full page reload/crash is NOT implemented — only within-attempt chunk retry is.** `@vercel/blob/client`'s high-level `upload()` (now with `multipart: true`) automatically retries failed *parts* during one call, which covers the common case (a flaky connection mid-upload). True resume-after-reload needs the SDK's low-level `createMultipartUpload`/`uploadPart`/`completeMultipartUpload` primitives plus a client token (`issueSignedToken`, not the `handleUploadUrl` flow already in use) and a local (e.g. IndexedDB) record of completed part ETags to resume from — a real rearchitecture of the upload flow that wasn't attempted this session because it hinges on an auth model (raw client tokens) not yet verified against a live Blob store. Revisit if large-upload drop-off turns out to matter in practice.
- **M8.4 retention has two separate halves that don't share a code path:** the Blob-hosted *upload* source is swept by a Vercel Cron job (`vercel.ts` → `/api/cron/retention`, daily, auth'd via `CRON_SECRET`); the worker-local cache of a *YouTube* source (see "worker-local source storage" above) is swept by the worker's own poll loop (`worker/retention.py`, hourly). Rendered clip outputs are deliberately untouched by both — the PRD's retention clause is specifically about *source* files, not the product's deliverable.
- **M8.7 i18n (English/French UI) is NOT implemented — no French translation exists anywhere in the app.** What IS real and verified: RTL-readiness for Arabic, specifically in the one place the PRD calls out (subtitle rendering) — `worker/subtitles.py`'s ASS burn-in via libass+fribidi+harfbuzz was pixel-verified with real Arabic text in M4/M6's integration tests. Translating every UI string and wiring an i18n framework (next-intl or similar) across every page is a substantial, separate effort that wasn't attempted here rather than half-done and presented as complete. Revisit as its own milestone slice before a French-market launch.
- **M8.8 accessibility: spot-checked and fixed what was found (a missing `aria-label` on the admin refund input), not a full WCAG AA audit.** The rest of the app already leans on native, keyboard-operable form elements (`<label>`-wrapped inputs, real `<button>`s via the shared `Button` component, real `<table>` markup in the admin view) and shadcn's default theme, which is contrast-conscious out of the box — but no automated contrast/keyboard-trap tooling (axe-core, Lighthouse) was run, since that needs a live rendered page, not just source review.
- **M8.9 E2E tests were NOT written.** They'd need a running Next.js app, a live Postgres, live Clerk, and a running worker — all blocked by the same Marketplace terms-acceptance issue that's blocked live testing since M1. Writing Playwright specs that have never actually run isn't meaningfully better than not having them (can't verify they'd even compile against real auth flows), so instead: the worker's `test_render_integration.py` suite *does* run for real (real ffmpeg, real MediaPipe, real pixel verification) and is the closest thing to integration coverage this session could actually execute. A real E2E pass — happy path (§4) + key edge cases, plus the 60-min-source/≤20-min NFR perf check — is the single biggest remaining pre-launch gap once infra is unblocked.
